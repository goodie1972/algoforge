# 对未来的构想

> 2026-06-11 讨论记录

## 当前架构回顾

```
MT4 (交易终端)
  ↑ TCP 23232 (EA 桥接插件)
  ↓
bridge.py ← → TradingEngine (engine_standalone/main.py)
                  ↑
                  ├── strategies/ (多因子评分、ATR止盈、RSI过滤等)
                  ├── data/database.py (SQLite 持久化)
                  ├── closed_trades.jsonl (成交流水)
                  └── dashboard/backend/ (FastAPI → Vue)
```

一切在本地 Windows 完成：EA 只在 MT4 里收发桥接消息，不做策略逻辑。策略计算、数据备份、Dashboard 全部由 Python 引擎处理。

## 多 EA 对接

当前架构本身就是解耦的，支持多终端接入改动不大：

```
MT4-A (EA) ─┐
MT4-B (EA) ─┤
MT4-C (EA) ─┼── bridge.py ── engine.py ── SQLite ── FastAPI ── Vue Dashboard
更多终端 ────┘
```

关键改动点：

1. **桥接层支持多连接** — 改为支持多个端口/IP，每个 EA 在独立 MT4 实例上监听不同端口
2. **策略池按来源路由** — `STRATEGY_POOL` 加 `bridge` 字段指定走哪个 MT4
3. **数据汇聚** — 所有终端数据入同一 SQLite，API 按 magic/strategy 区分，前端无需改造
4. **跨 EA 风控** — 引擎统一做总仓位控制、总体浮亏上限

## 性能瓶颈分析

### Python 扛得住吗？

当前负载（M30/H1 策略，~1 秒循环）对 Python 来说非常轻松。一次循环中策略计算 < 5ms，其余 995ms 在 sleep。

10 个 EA 的场景：
- 10 × 1 次/秒 = 10 次循环/秒
- 每次拉 K 线 + 算指标 + 检查持仓 ≈ 10ms
- CPU 占用 ~10%

结论：**绰绰有余。**

### 瓶颈到底在哪

| 场景 | Python 表现 | 真正瓶颈 |
|------|-----------|---------|
| 10 EA + M30/H1 | 无压力 | MT4 单线程图表 |
| Tick 级策略 (ms级) | 吃紧 | TCP 序列化 + JSON 编解码 |
| 大规模回测 | 是瓶颈，但换语言也差不多 | 指标计算本身 |
| 实时 ML 推理 | 看模型规模 | 换 C++ 推理库才有意义 |

### 换 Go/Rust 有必要吗？

对当前场景意义不大。Go 并发模型漂亮，Rust 性能强，但瓶颈不在语言层面。

更高性价比的优化方向：
1. **缩短桥接路径** — MT4 EA 用 C++ 插件代替 MQL4
2. **数据本地缓存** — 已实现（SQLite 跨周期读 H1）
3. **请求批处理** — 多策略合并一次 TCP 往返

### 桥接延迟具体数据

- 单次 TCP 请求 (localhost): < 0.1ms
- 单次拉 200 根 K 线: 几十 KB
- MQL4 图表线程是单线程的——同一 EA 并发请求会排队
- 多 MT4 实例天然并行（各自独立图表线程）

### 结论

Python 作为策略引擎语言完全够用。**换语言解决不了我们的瓶颈**——真正限制在 MT4 单线程架构。除非上毫秒级 tick 策略 + 实时深度学习推理，否则 Python 是合理的选择。

## 策略放 MT4 里不行吗？

当前架构本质是**专业算法交易架构**：MT4 做执行网关，Python 做策略引擎 + 风控 + 数据持久化 + Dashboard。优势：

- Python 生态丰富（SQLite、JSON、机器学习库）
- 多策略协调统一（跨策略风控、新闻事件处理）
- 数据自己掌控，不绑死在一个终端里
- 换 broker 只需换桥接，策略不动

不是 MT5 的逻辑——更像 hedge fund 的算法交易架构。MT5 改进有限，本质还是 EA 跑在终端里，用 MQL 写逻辑。
